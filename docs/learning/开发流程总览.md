# Gateway 开发流程总览（需求 -> 设计 -> 代码 -> 证据）

## 1. 先看这张流程图
```text
需求文档(FR/NFR/AC)
        |
        v
概要设计(01) -> 任务分解(02) -> 详细设计(03)
        |                          |
        +-------------> 任务实现(Tx-xxx) + 测试
                                   |
                                   v
                    追踪矩阵回填(代码/测试/证据/状态)
                                   |
                                   v
                           Gate 结论(GateStatus)
                                   |
                 +-----------------+-----------------+
                 |                                   |
                 v                                   v
      run-quality.sh(代码质量)         verify-stage.sh --strict(流程闭环)
                 |                                   |
                 +-----------------+-----------------+
                                   |
                                   v
                              commit / push
```

## 2. 放行条件可视化（能不能提交）
```text
GateStatus=PASS ?
    ├─ 否 -> 不允许提交
    └─ 是
        |
矩阵所有状态=PASS 且 代码/测试/证据不为空 ?
    ├─ 否 -> 不允许提交
    └─ 是
        |
run-quality.sh 通过 ?
    ├─ 否 -> 不允许提交
    └─ 是 -> 允许提交
```

## 3. 核心名词（先统一语言）
- `FR`：功能需求（功能上要做到什么）。
- `NFR`：非功能需求（性能、稳定性、可维护性等）。
- `AC`：验收标准（如何判定“完成”）。
- `T1-xxx`：阶段任务 ID（具体实现动作）。
- `追踪矩阵`：把“需求 -> 任务 -> 代码 -> 测试 -> 证据”串起来的总账本。
- `GateStatus`：阶段放行状态（`PENDING/PASS/FAIL`）。

## 4. 每个阶段必须产出的文件
- 需求：`docs/requirements/01-阶段X-...md`
- Gate：`docs/requirements/stage-gates/阶段X-Gate.md`
- 追踪矩阵：`docs/requirements/traceability/阶段X-需求追踪矩阵.tsv`
- 概要设计：`docs/design/stageX/01-阶段X-概要设计.md`
- 任务分解：`docs/design/stageX/02-阶段X-任务分解.md`
- 详细设计：`docs/design/stageX/03-阶段X-详细设计.md`
- 阶段学习文档：`docs/learning/stageX/`
- 阶段看板（双看板，强制同步）：
  - 开发流程看板：`docs/learning/stageX/06-阶段X开发流程可视化.html`
  - 学习指导看板：`docs/learning/stageX/07-阶段X学习指导看板.html`

## 5. 标准执行顺序（强约束）
1. 先写需求（FR/NFR/AC）。
2. 写概要设计与详细设计。
3. 拆任务并标注依赖（先后顺序）。
4. 按任务顺序编码与测试。
5. 回填追踪矩阵（代码位置、测试、证据、状态）。
6. 更新 GateStatus。
7. 同步更新阶段双看板（06 开发流程看板 + 07 学习指导看板）。
8. 执行双校验（代码质量 + 流程闭环）。
9. 校验通过后提交与推送。

## 6. 双校验分别在卡什么
### 6.1 代码质量校验
命令：
```bash
./scripts/ci/run-quality.sh
```
它会触发 Maven `quality` profile，拦截：
- 格式与规范：Spotless / Checkstyle / License Header
- 测试：Surefire / Failsafe
- 静态分析：PMD / SpotBugs
- 覆盖率：JaCoCo 阈值

### 6.2 流程闭环校验
命令：
```bash
./scripts/requirements/verify-stage.sh 1 --strict
```
`--strict` 重点检查：
- GateStatus 必须为 `PASS`
- 追踪矩阵每条状态必须 `PASS`
- 追踪矩阵每条 `代码实现/测试用例/证据` 不得为空或“待补充”
- 需求文档里的 FR/NFR/AC ID 必须都在追踪矩阵里出现

## 7. 如何判断“这阶段可提交”
必须同时满足：
1. `./scripts/ci/run-quality.sh` 通过
2. `./scripts/requirements/verify-stage.sh <stage> --strict` 通过
3. GateStatus=`PASS`
4. 追踪矩阵对应需求状态为 `PASS`
5. 重大代码变更已同步设计文档、追踪矩阵、学习文档、README
6. 阶段双看板（06/07）已同步更新

## 8. 新人最容易踩坑的点
- 只改代码不回填追踪矩阵，`--strict` 会失败。
- Gate 没改成 `PASS`，`--strict` 会失败。
- 需求新增了 ID，但矩阵没补，`verify-stage.sh` 会失败。
- 重大改动没同步学习文档/README，后续维护者读不懂上下文。

## 9. 最小执行清单（可直接照做）
```bash
# 1) 代码质量
./scripts/ci/run-quality.sh

# 2) 阶段闭环
./scripts/requirements/verify-stage.sh 1 --strict

# 3) 通过后再提交
git add -A
git commit -m "feat(stage1): xxx"
git push origin <branch>
```
