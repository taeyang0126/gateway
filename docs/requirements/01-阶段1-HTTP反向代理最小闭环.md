# 阶段 1 需求：HTTP 反向代理最小闭环

## 1. 阶段目标
- 建立可运行的 Netty 网关主链路，实现 HTTP 请求到上游服务的反向代理。
- 完成最小可用版本（MVP），作为后续所有能力的基础。

## 2. 范围
### 2.1 In Scope
- 单协议：HTTP/1.1
- 单实例网关部署
- 静态上游配置（单服务、可扩展为多实例）
- 基础连接池与超时控制
- 基础访问日志与错误处理
- 管理端点（`/health`、`/metrics/prometheus`）与基础访问控制
- 单路由待转发请求队列有界保护（防止上游慢导致内存放大）

### 2.2 Out of Scope
- 动态服务发现
- WebSocket/TCP 长连接代理
- 限流、熔断、鉴权等治理能力

## 3. 功能需求
- `FR-1-1` 网关必须基于 Netty 启动 HTTP Server，支持 Keep-Alive。
- `FR-1-2` 网关必须支持将请求按固定路由规则转发到上游 HTTP 服务。
- `FR-1-3` 网关必须透传以下信息：请求方法、路径、Query、Body。
- `FR-1-4` 网关必须按 RFC 规则处理 Header：
  - 必须移除 Hop-by-Hop 头（`Connection`、`Keep-Alive`、`TE`、`Trailer`、`Upgrade`、`Proxy-Authenticate`、`Proxy-Authorization`、`Transfer-Encoding`）。
  - 必须写入或追加 `X-Forwarded-For`、`X-Forwarded-Proto`、`X-Forwarded-Host`。
  - 必须定义 `Host` 透传或重写策略（路由可配置，默认重写为上游主机）。
  - 必须透传或生成 `TraceId` 并在响应日志中关联。
- `FR-1-5` 网关必须处理上游响应并回传状态码、Header、Body。
- `FR-1-6` 网关必须提供连接超时、读取超时、写入超时配置项。
- `FR-1-7` 网关必须记录访问日志，至少包含 traceId、URI、状态码、耗时、上游地址。
- `FR-1-8` 网关必须提供健康检查接口 `/health`。
- `FR-1-9` 网关必须区分网关错误和上游错误，并返回统一错误响应格式。

## 4. 非功能需求
- `NFR-1-1` 严禁在 Netty EventLoop 中执行阻塞操作。
- `NFR-1-2` 默认启用池化内存分配器 `PooledByteBufAllocator`。
- `NFR-1-3` 在 2C4G 开发机环境下，压测目标为：
  - 稳态吞吐不低于 2,000 RPS（1KB 小包）
  - `p99` 网关附加延迟不高于 20ms
- `NFR-1-4` 异常场景稳定性阈值（10 分钟压测窗口）：
  - 进程 RSS 相比第 5 分钟基线增幅不超过 15%。
  - FD 数量在稳态窗口内波动不超过 ±10%。
  - GC 单次暂停（STW）`p99` 不超过 200ms。

## 5. 验收标准
- `AC-1-1` 请求 `GET /api/ping` 可被成功转发到上游并返回 200。
- `AC-1-2` 上游不可达时，网关返回统一 502 错误结构，日志记录失败原因。
- `AC-1-3` 配置 1s 超时后，上游超时请求在 1s~1.2s 内失败返回。
- `AC-1-4` 连续压测 10 分钟后满足：
  - 稳态吞吐不低于 2,000 RPS（1KB 小包），且 `p99` 网关附加延迟不高于 20ms。
  - 无 OOM、无连接泄漏。
  - RSS 增幅、FD 波动、GC 暂停满足 `NFR-1-4` 阈值。

## 6. 测试要求
- 单元测试：
  - 路由匹配
  - 请求头透传
  - Hop-by-Hop 头移除与 `X-Forwarded-*` 写入
  - 超时处理
- 集成测试：
  - 网关到 mock 上游的端到端代理
  - 上游失败场景（超时、连接拒绝、5xx）

## 7. 设计输入清单
- 启动流程与生命周期图
- Netty Pipeline 处理链定义
- 请求上下文模型（RequestContext）
- 上游连接池抽象接口定义
- 错误码与错误响应模型

## 8. 风险与约束
- `RISK-1-1` 若模型设计过早追求插件化，可能拖慢 MVP 交付。
- `RISK-1-2` 若忽略超时分层，会导致故障放大和线程堆积。
