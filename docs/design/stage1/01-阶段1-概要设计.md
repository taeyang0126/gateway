# 阶段 1 概要设计（HTTP 反向代理最小闭环）

## 1. 设计目标
- 基于 Netty 实现 HTTP/1.1 反向代理主链路，覆盖 `FR-1-1` ~ `FR-1-9`。
- 提供可直接进入详细设计与编码的结构化输入，保证阶段 1 可验收、可追踪。

## 2. 设计边界
- In Scope：单实例、静态路由、HTTP/1.1、连接池、超时控制、访问日志、`/health`。
- Out of Scope：服务发现、WebSocket/TCP、限流熔断鉴权、多实例一致性。

## 3. 总体架构
### 3.1 组件划分
- `GatewayBootstrap`：应用启动、端口监听、生命周期管理。
- `ServerPipelineFactory`：定义服务端 Netty Pipeline。
- `ProxyFrontendHandler`：请求接入与转发编排入口。
- `RouteService`：静态路由匹配与上游地址决策。
- `HeaderPolicyService`：Hop-by-Hop 头移除、`X-Forwarded-*` 写入、`Host` 策略处理。
- `TraceService`：透传或生成 `TraceId`，并在日志链路统一关联。
- `UpstreamClientPool`：上游连接复用、连接创建与回收。
- `TimeoutPolicy`：连接/读/写超时策略定义与执行。
- `ErrorResponseMapper`：网关错误与上游错误分类映射为统一响应结构。
- `AccessLogService`：记录 traceId、URI、状态码、耗时、上游地址。
- `HealthHandler`：处理 `/health` 快速返回。

### 3.2 运行时链路
```text
Client
  -> NettyServer(HttpServerCodec + Aggregator)
  -> RequestContext(traceId/startAt/clientIp)
  -> HealthHandler(/health 短路)
  -> RouteService(静态路由)
  -> HeaderPolicyService(移除 Hop-by-Hop + 写入 X-Forwarded-*)
  -> UpstreamClientPool(获取或建立连接)
  -> Upstream Request/Response
  -> ErrorResponseMapper(仅在失败分支)
  -> AccessLogService
  -> Client Response
```

## 4. Pipeline 设计
### 4.1 服务端 Pipeline
1. `HttpServerCodec`
2. `HttpObjectAggregator`（限制 `maxContentLength`）
3. `RequestContextInitHandler`
4. `HealthHandler`
5. `ProxyFrontendHandler`
6. `GlobalExceptionHandler`

### 4.2 上游客户端 Pipeline
1. `HttpClientCodec`
2. `HttpObjectAggregator`（限制 `maxContentLength`）
3. `UpstreamResponseHandler`
4. `UpstreamExceptionHandler`

## 5. 核心模型
### 5.1 RequestContext
- `traceId`
- `startTimeNanos`
- `clientIp`
- `requestMethod`
- `rawPath`
- `queryString`
- `targetUpstream`
- `routeId`

### 5.2 错误响应模型
- 字段：`timestamp`、`traceId`、`category`、`code`、`message`、`status`
- 分类：
  - `GATEWAY_ERROR`：网关内部错误、协议错误、非法请求
  - `UPSTREAM_ERROR`：上游不可达、超时、连接失败

## 6. 关键策略
### 6.1 路由匹配策略（`FR-1-2`）
- 按业界主流策略执行以下顺序：
  1. 先按 `priority`（数值越大优先级越高）排序。
  2. 再按匹配类型：`EXACT` 优先于 `PREFIX`。
  3. 在 `PREFIX` 中按“最长前缀优先”。
  4. 仍冲突时按配置声明顺序选择第一条。
- 推荐默认兜底路由：`/`。

### 6.2 Header 策略（`FR-1-4`）
- 必删 Hop-by-Hop：
  - `Connection`
  - `Keep-Alive`
  - `TE`
  - `Trailer`
  - `Upgrade`
  - `Proxy-Authenticate`
  - `Proxy-Authorization`
  - `Transfer-Encoding`
- 追加或写入：
  - `X-Forwarded-For`
  - `X-Forwarded-Proto`
  - `X-Forwarded-Host`
- 可选写入标准头 `Forwarded`（`for`/`proto`/`host`），但阶段 1 以 `X-Forwarded-*` 为主。
- `Host` 策略：默认重写为上游主机，保留路由级开关（`REWRITE` / `PRESERVE`）。
- `TraceId`：固定请求头名称 `X-Trace-Id`，优先透传，缺失时生成并注入上下文。

### 6.3 超时策略（`FR-1-6`）
- 连接超时：控制建连时间上限。
- 读超时：控制等待上游响应时间上限。
- 写超时：控制请求写入上游时间上限。
- 阶段 1 默认目标：支持将超时阈值设置为 1s，用于 `AC-1-3` 验收。

### 6.4 统一错误映射（`FR-1-9`）
- 上游不可达/连接拒绝：`502`
- 上游超时：`504`
- 网关内部异常：`500`
- 请求非法：`400`

## 7. 非功能落地点
- `NFR-1-1`：禁止阻塞 EventLoop；禁止在 Handler 内进行阻塞 IO。
- `NFR-1-2`：默认启用 `PooledByteBufAllocator`。
- `NFR-1-3`：以压测脚本验证 2000 RPS 与 `p99 <= 20ms`。
- `NFR-1-4`：10 分钟稳定性窗口采集 RSS、FD、GC 指标并与阈值比对。

## 8. 需求可追踪映射
- `FR-1-1`：`GatewayBootstrap`、服务端 Pipeline Keep-Alive
- `FR-1-2`：`RouteService` + `ProxyFrontendHandler`
- `FR-1-3`：`ProxyFrontendHandler` 请求透传逻辑
- `FR-1-4`：`HeaderPolicyService` + `TraceService`
- `FR-1-5`：`UpstreamResponseHandler` + 回写逻辑
- `FR-1-6`：`TimeoutPolicy`
- `FR-1-7`：`AccessLogService`
- `FR-1-8`：`HealthHandler`
- `FR-1-9`：`ErrorResponseMapper`

## 9. 已确认决策
- 路由匹配策略：`priority -> EXACT -> PREFIX(最长前缀优先) -> 声明顺序`。
- TraceId 头固定为 `X-Trace-Id`。
- Host 策略采用“默认 `REWRITE`，并将原始 Host 写入 `X-Forwarded-Host`”。
- Host 路由级开关配置名称采用 `hostRewriteMode`。
