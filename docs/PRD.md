# Gateway V3 需求文档（精简版）

## 1. 文档信息
- 版本：v2.2
- 日期：2026-03-18
- 目标：定义 IM + API 一体化网关的需求边界与验收标准
- 约束：本文仅描述需求，不描述实现方案

## 2. 已确认决策（来自 lei）
1. 业务范围：IM + API。
2. 长连接协议：WebSocket。
3. 服务发现与配置中心：Nacos。
4. 消息语义：设备级恰好一次（7 天窗口）。
5. 顺序语义：会话内有序。
6. 推送目标：到达率优先。
7. 资源基线：单 Pod 2C4G。
8. 技术基线：Java + JDK 24 + Netty 4.2.x + Spring Boot。
9. 管理控制台形态：按租户管理。
10. 变更审批：支持审批流，但不强制双人复核。
11. 灰度策略：优先按租户灰度，租户内支持按流量比例与实例标签灰度。
12. 管理范围：纳入网关管理页面（含代理配置与 IM 专项管理能力）。

## 2.1 术语与口径（需求定义）
1. 设备级恰好一次（7 天窗口）：同一业务消息在同一目标设备上，在 7 天内最多生效一次。
2. 会话内有序：同一会话内，同一接收侧观察到的消息顺序必须与发送顺序一致。
3. 到达率：在目标时间窗口内，消息成功送达目标设备的比例。
4. 在线消息投递时延：从网关受理发送请求到目标终端确认接收的时延。
5. 语义一致：SDK、HTTP API、RPC、MQ 四种接入方式在请求语义、错误码语义、回执语义上保持一致。
6. 核心链路追踪覆盖率：核心链路中可完成端到端关联追踪的请求占比。
7. 会话恢复成功：终端重连后在规定恢复时限内恢复到可收发状态，且恢复前后无重复生效、无消息丢失。

## 3. 范围与边界
### 3.1 范围内
1. 接入网关面：终端连接接入与连接治理。
2. 业务网关面：上游服务调用接入与统一治理。
3. IM 在线消息链路、离线补偿链路、状态回执与审计追踪。
4. API 代理、服务发现、配置动态生效。

### 3.2 范围外
1. 不定义数据库表结构与代码级协议字段。
2. 不定义具体部署拓扑与中间件选型细节。
3. 不定义业务客户端 UI 与业务页面需求；本 PRD 包含网关管理控制台页面需求。

## 4. 总体需求
1. 系统必须同时提供“接入网关面”和“业务网关面”两类能力。
2. 终端必须通过 WebSocket 与网关维持长连接。
3. IM 核心服务必须与网关保持实时协同通道，保障在线消息实时下发。
4. 上游普通业务服务默认通过 HTTP/RPC 无状态调用网关能力，不要求与网关长连接。
5. 系统在 V1 阶段必须支持上游通过 SDK、HTTP API、RPC、MQ 四种方式接入推送服务，且语义一致。
6. IM 核心服务与推送服务必须解耦为独立服务：IM 核心仅负责 IM 语义，推送服务仅负责投递编排。

## 5. 功能需求
### 5.1 接入网关面
1. 必须支持连接建立、鉴权、保活、断线重连、会话恢复。
2. 必须支持在线状态判定与状态变更通知。
3. 必须支持连接级限流、黑白名单与异常连接治理。
4. 必须支持连接与会话维度的追踪查询。

### 5.2 业务网关面
1. 必须提供 API 统一入口与路由转发能力。
2. 必须支持上游服务健康摘除与流量切换。
3. 必须支持路由/策略变更的灰度生效与回滚。
4. 必须提供统一错误码与统一回执语义。

### 5.3 上游接入能力
1. 必须提供 SDK、HTTP API、RPC、MQ 四种接入方式。
2. 四种接入方式必须保证请求语义、错误码语义、回执语义一致。
3. 必须支持单播、群发、广播三类消息发送请求。
4. 请求必须包含幂等标识和全链路追踪标识。

### 5.4 IM 消息能力
1. 必须支持在线投递与离线补偿。
2. 必须支持接收回执与回执查询。
3. 必须满足设备级恰好一次语义（7 天窗口）。
4. 必须满足会话内有序语义。
5. 必须支持消息过期策略与可审计查询。

### 5.5 IM 核心服务与推送服务边界
1. IM 核心服务仅负责 IM 领域能力：会话、序列、ACK、已读、消息语义校验。
2. 推送服务仅负责投递领域能力：通道选择、投递编排、重试、限流、回执聚合。
3. 上游服务发送消息默认接入推送服务；推送服务与 IM 核心服务通过契约接口协同。
4. 推送服务必须支持在线投递与离线补偿协同，不改变 IM 核心语义定义。

### 5.6 服务发现与配置
1. 必须使用 Nacos 作为服务发现来源。
2. 必须使用 Nacos 作为配置动态下发来源。
3. 仅允许将流量路由到健康实例。
4. 必须支持按标签/版本的流量策略。

### 5.7 多租户治理
1. 必须支持配置隔离、流量隔离、数据隔离、权限隔离、审计隔离。
2. 必须支持租户级配额与限流，避免单租户影响全局。
3. 必须支持租户维度的审计追溯。

### 5.8 接入网关连接迁移与无感恢复
1. 接入网关必须支持节点状态流转：Active、Draining、Out。
2. 节点进入 Draining 后必须停止接收新连接，存量连接按策略自然排空。
3. 节点故障或下线时，客户端必须自动重连并恢复会话。
4. 会话恢复必须保证恢复前后消息语义连续，避免重复生效与消息丢失。
5. 扩容、缩容、故障切换期间必须满足既定连接可用性与恢复时延指标。
6. 会话恢复成功判定必须统一：恢复后连接可用、消息可收发，且满足 6.2 节恢复时延指标。

### 5.9 网关管理控制台（按租户）
1. 必须提供按租户隔离的管理控制台；租户管理员仅可见并操作本租户配置与数据。
2. 必须支持代理路由配置管理：创建、编辑、删除、查询、版本对比。
3. 必须支持路由匹配规则配置：Path、Host、Method、Header、Query。
4. 必须支持代理策略配置：超时、重试、熔断、限流、黑白名单、鉴权策略。
5. 必须支持 Nacos 服务选择与实例健康可视化，仅允许路由到健康实例。
6. 必须支持配置版本化：草稿、预检、发布、回滚；每次发布必须生成可追溯版本号。
7. 必须支持灰度发布：按租户灰度为主；租户内支持按流量比例（如 5/25/50/100）和实例标签灰度。
8. 必须支持统一审计：记录操作者、时间、变更内容、审批信息（如有）、发布结果与关联 traceId。
9. 必须支持权限模型：平台管理员、租户管理员、审计只读角色，并支持最小权限原则。
10. 必须纳入 IM 专项管理页面：在线会话查询、消息投递轨迹查询、离线补偿任务查询与重放。

## 6. 非功能需求
### 6.1 可观测性
1. 必须具备结构化日志、指标、链路追踪、审计四类能力。
2. 日志至少包含：traceId、tenantId、deviceId、resultCode、latency。
3. 核心链路必须可按 traceId 回放。
4. 必须具备告警分级（P1/P2/P3）与升级机制。

### 6.2 性能与容量（单 Pod 2C4G 基线）
1. WebSocket 活跃连接：>= 20,000。
2. 新建连接峰值：>= 1,000 次/秒（持续 5 分钟）。
3. API 代理吞吐：>= 3,000 RPS（小报文，单请求体 <= 1KB）。
4. IM 消息处理吞吐：>= 5,000 条/秒。
5. 在线消息投递时延：P99 <= 3 秒（同城网络条件）。
6. 重连恢复时延：P95 <= 3 秒，P99 <= 8 秒。
7. 月可用性：>= 99.95%。
8. 节点扩缩容或单节点故障期间，连接恢复成功率：>= 99.9%。

### 6.3 安全与合规
1. 必须全链路加密传输。
2. 必须统一连接鉴权与接口鉴权。
3. 必须具备限流、防重放、防暴力尝试能力。
4. 必须具备密钥轮换与安全审计。
5. 安全基线必须对齐 OWASP ASVS 与 OWASP API Security Top 10。

### 6.4 工程质量
1. 后端必须以 Maven 作为构建入口；前端构建需纳入统一 CI 质量门禁并可追溯。
2. 必须有依赖收敛与版本锁定机制。
3. 必须有静态检查、测试、风格检查发布门禁。
4. 禁止 SNAPSHOT 进入正式发布链路。
5. 构建产物必须可追溯、可复现。

### 6.5 指标统计口径
1. 所有性能指标统计窗口必须在同一压测窗口内统一计算。
2. 可用性指标统计窗口为自然月。
3. 恢复成功率的分母为受影响连接总数。
4. 核心链路追踪覆盖率的分母为核心链路总请求数。
5. 同城网络条件统一定义为：单可用区网络环境，RTT P95 <= 20ms，丢包率 <= 0.1%，无持续性网络故障。
6. 实时通道“持续传输”验收统计窗口为连续 24 小时。
7. 重复生效率与消息丢失率按有效发送消息总量统计，验收样本量不少于 1,000,000 条有效消息。

### 6.6 管理控制台非功能
1. 管理控制台关键页面加载时延：P95 <= 2 秒（同城网络条件，首屏可交互）。
2. 路由配置查询与版本对比操作时延：P95 <= 1 秒（单租户常规数据规模）。
3. 所有配置变更操作必须具备二次确认机制与防误操作提示。
4. 管理控制台关键操作必须全量审计，审计记录保留周期不少于 180 天。
5. 管理控制台权限校验必须前后端一致，禁止仅前端拦截。

## 7. 验收标准
### 7.1 功能验收
1. 接入网关面与业务网关面能力均可独立验收，且能力项通过率为 100%。
2. 终端 WebSocket 长连接全流程（建连、鉴权、保活、重连、恢复）必须通过验收，建连成功率与重连成功率均 >= 99.9%。
3. IM 核心服务到网关实时通道必须在连续 24 小时窗口内满足持续传输要求；单次异常场景恢复时限 <= 60 秒，且恢复后消息无丢失。
4. SDK/HTTP/RPC/MQ 四通道语义一致性必须通过验收，结果语义一致率为 100%。
5. 设备级恰好一次与会话内有序场景必须通过验收；在 7 天窗口且不少于 1,000,000 条有效消息样本下，重复生效率目标为 0，消息丢失率目标为 0，并按 6.5 节统计口径与异常归因规则统一判定。
6. IM 核心服务与推送服务职责边界用例必须通过验收，职责越界行为不允许出现。
7. 节点扩容、缩容、故障场景下连接迁移与会话恢复必须通过验收，恢复成功率 >= 99.9%。

### 7.2 管理控制台验收
1. 按租户隔离必须通过验收：A 租户不可查看或操作 B 租户配置与审计数据。
2. 代理配置全流程必须通过验收：创建、预检、灰度发布、全量发布、回滚能力通过率 100%。
3. 灰度策略必须通过验收：支持按租户、按流量比例、按实例标签三个维度；触发阈值后可自动回滚。
4. 审计检索必须通过验收：可按 tenantId、operator、traceId、版本号检索并回放关键变更。
5. IM 专项管理页面必须通过验收：在线会话、投递轨迹、离线补偿任务查询与重放能力可用。

### 7.3 非功能验收
1. 6.2 节容量与时延指标全部达标。
2. 核心链路追踪覆盖率 >= 95%。
3. 安全基线核查通过率 100%。
4. 发布门禁全部通过方可发布。
5. 6.2.5 的时延验收必须在 6.5.5 定义的同城网络条件下执行并判定。

## 8. 分期规划
分期说明：第 4 章定义的是全量目标，按分期逐步达成；V1 达成四种接入方式全覆盖。

### 8.1 MVP
1. 接入网关面与业务网关面基础能力。
2. 终端 WebSocket 长连接全生命周期。
3. 上游 SDK + HTTP 接入。
4. 在线投递 + 离线补偿基础能力。
5. 设备级恰好一次（7 天）与会话内有序基础能力。
6. 基础可观测与安全门禁。
7. 管理控制台 MVP：按租户路由配置管理、版本发布回滚、基础审计。

### 8.2 V1
1. RPC + MQ 接入补齐并与 SDK/HTTP 语义对齐。
2. 群发/广播与策略化投递增强。
3. 多租户治理增强与报表能力。
4. 稳定性演练与补偿机制增强。
5. 管理控制台 V1：灰度发布增强（租户/比例/标签）、审批流（可选）、告警联动。
6. IM 专项管理 V1：投递轨迹与离线补偿任务可视化闭环。

### 8.3 V2
1. 更高等级可用性与容灾目标。
2. 平台化自助治理与租户精细化运营。
3. 管理控制台 V2：变更影响分析与策略推荐能力。

## 9. 风险与待持续确认
1. 2C4G 指标需结合真实业务模型持续校准。
2. 到达率优先可能影响实时性，需要业务侧容忍阈值。
3. 设备标识稳定性会影响设备级恰好一次语义准确性。
4. 会话内有序在大群高并发场景需持续压测验证。
5. 推送服务与 IM 核心服务契约变更需有严格版本治理，避免跨服务语义漂移。
