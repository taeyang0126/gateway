# Gateway V3 需求文档（PRD）

## 1. 文档信息
- 项目：Gateway V3
- 文档版本：v1.0
- 日期：2026-03-18
- 目标：定义 IM + API 一体化网关的需求边界、验收标准与分期目标
- 当前阶段：仅需求定义，不涉及实现细节

## 2. 已确认决策（来自 lei）
1. 业务范围：IM + API 都要做。
2. 长连接协议：WebSocket。
3. 服务发现与配置中心：Nacos。
4. 消息语义：设备级恰好一次（Business Exactly-Once）。
5. 去重窗口：7 天。
6. 顺序语义：会话内有序（不承诺全局有序）。
7. 推送目标优先级：到达率优先（高于实时性）。
8. 资源基线：单 Pod 规格为 2C4G（后续容量指标按该规格标定）。

## 3. 目标与非目标
### 3.1 目标
1. 提供统一入口，支持 API 代理与 IM 长连接接入。
2. 支持上游服务代理与基于 Nacos 的服务发现。
3. 提供 IM 消息收发、离线补偿、状态回执与可追溯审计。
4. 在设备维度达成“恰好一次业务生效”语义。
5. 满足可观测性、性能、安全三大非功能要求，并达到业界主流水平。

### 3.2 非目标
1. 本阶段不定义具体技术实现方案与组件选型细节。
2. 本阶段不定义详细数据库表结构、协议字段与代码架构。
3. 本阶段不覆盖客户端 SDK 设计细节。

## 4. 关键术语定义
### 4.1 设备级恰好一次（Business Exactly-Once）
对同一设备上的同一业务意图（`tenantId + deviceId + eventType + eventId`），在 7 天窗口内只允许一次业务生效提交；允许网络层重试，但不允许产生重复生效记录。

### 4.2 会话内有序
同一会话（单聊会话或群会话）内消息顺序可依序恢复与消费；不同会话之间不承诺全局顺序。

### 4.3 在线状态判定（补充解释）
在线状态用于业务侧判断用户终端可达性，定义如下：
1. 客户端连接建立且鉴权通过后记为在线。
2. 连续心跳超时达到阈值后记为离线。
3. 断线后重连成功并恢复会话记为在线恢复。

注：本项是你在第 4 点“没看懂”的补充说明，下面会给出验收口径。

### 4.4 多租户（补充解释）
多租户指多个业务方（Tenant）共享同一网关集群，但在配置、流量、数据、权限、审计上进行逻辑隔离，避免互相影响。

## 5. 角色与价值
1. 业务接入方（后端研发/架构师）：通过统一网关接入，降低上游服务变化对业务的影响。
2. IM 产品与运营：通过稳定在线与高到达率推送提升活跃与留存。
3. SRE/运维：通过可观测、可告警、可审计机制快速定位与止损。
4. 安全与平台治理：通过统一鉴权、租户隔离和审计满足合规要求。

## 6. 功能需求
### 6.1 API 代理能力
1. 提供统一入口接收 API 请求并按路由规则代理上游服务。
2. 支持路由变更与回退能力（需求层面定义为可控发布与可审计）。
3. 支持异常上游实例摘除与健康流量转移。

### 6.2 服务注册发现（Nacos）
1. 网关以 Nacos 作为服务实例发现来源。
2. 网关以 Nacos 作为配置动态下发来源。
3. 网关仅向健康实例分发流量。
4. 支持基于标签/版本的流量策略（需求约束，细节后续设计）。

### 6.3 IM 长连接（WebSocket）
1. 支持连接建立、鉴权、保活、断线重连、会话恢复。
2. 支持在线状态查询与状态变更通知。
3. 支持多端并发连接（设备级语义下按设备独立管理）。
4. 支持连接质量监控（建立成功率、断连率、重连成功率）。

### 6.4 IM 消息生命周期
1. 消息发送：接收消息并分配全局可追踪标识。
2. 消息投递：在线投递与离线暂存。
3. 消息回执：至少包含接收回执与展示回执。
4. 消息重试：允许重试但必须满足设备级幂等生效。
5. 消息过期：支持 TTL 与过期后审计可查。

### 6.5 推送能力（到达率优先）
1. 支持在线直达与离线补偿协同。
2. 支持单播、群发、广播三类推送形态。
3. 支持推送状态追踪：发送、投递、到达、失败原因。
4. 以到达率为首要优化目标，实时性为次优目标。

### 6.6 多租户治理
1. 配置隔离：各租户路由、限流、鉴权策略独立。
2. 流量隔离：租户级配额与限流，防止单租户冲击全局。
3. 数据隔离：日志、消息轨迹、审计信息按租户可隔离检索。
4. 权限隔离：租户管理员权限边界清晰，禁止跨租户操作。
5. 审计隔离：敏感操作可按租户独立追溯。

## 7. 非功能需求
### 7.1 可观测性
1. 必须具备结构化日志（含 traceId、tenantId、deviceId、resultCode、latency）。
2. 必须具备指标体系（连接、请求、错误、时延、队列积压、资源水位）。
3. 必须具备链路追踪能力，核心链路可回放。
4. 必须具备告警分级与升级机制（P1/P2/P3）。
5. 必须具备审计能力，敏感操作可追责。

### 7.2 性能与容量（2C4G 单 Pod 基线）
以下为初始需求基线，后续可在压测后校准：
1. WebSocket 连接容量（稳态）：单 Pod >= 20,000 活跃连接。
2. 新建连接速率（峰值）：单 Pod >= 1,000 次/秒（持续 5 分钟）。
3. API 代理吞吐（稳态）：单 Pod >= 3,000 RPS（小报文场景）。
4. IM 消息处理吞吐（稳态）：单 Pod >= 5,000 条/秒（含入站与投递处理）。
5. 端到端消息可查询生效时延：P99 <= 3 秒（同城）。
6. 在线恢复时延：断线重连后会话恢复 P95 <= 3 秒，P99 <= 8 秒。
7. 可用性目标：月度可用性 >= 99.95%。

说明：这些值是需求签约起点，不是最终承诺上限，最终以压测报告与业务规模复核。

### 7.3 安全
1. 所有外部链路必须加密传输。
2. 连接鉴权、接口鉴权必须统一策略。
3. 必须具备限流、防重放、防暴力尝试能力。
4. 必须支持密钥轮换与审计记录。
5. 必须支持租户级访问控制与越权拦截。

### 7.4 工程治理（Maven 强制）
1. Maven 作为唯一构建入口。
2. 统一父 POM 与依赖版本管理。
3. 强制静态检查、测试、风格检查作为发布门禁。
4. 禁止 SNAPSHOT 进入正式发布链路。
5. 构建过程可复现，产物元数据可追踪。

## 8. 验收标准（需求验收口径）
### 8.1 功能验收
1. API 请求可按路由转发到 Nacos 注册服务，并具备异常实例摘除行为。
2. WebSocket 连接可完成建连、鉴权、保活、重连、恢复全流程。
3. 消息支持在线/离线投递与状态回执。
4. 在 7 天窗口内，同一设备同一业务事件不产生重复业务生效记录。
5. 同一会话消息顺序满足既定规则。

### 8.2 非功能验收
1. 核心链路具备日志、指标、追踪、审计四类观测数据。
2. 2C4G 单 Pod 达到第 7.2 节定义的容量与时延基线。
3. 高优先级安全检查项无阻断级问题。
4. 发布流水线的质量门禁全部通过。

## 9. 分期规划
### 9.1 MVP
1. API 代理 + Nacos 发现/配置。
2. WebSocket 长连接全生命周期。
3. 单播为主的在线/离线消息能力。
4. 设备级恰好一次（7 天窗口）基础能力。
5. 基础可观测与安全能力。

### 9.2 V1
1. 群发/广播与策略化投递。
2. 多租户配额与治理增强。
3. 推送漏斗报表与更完整运营分析。
4. 更完善的故障补偿与演练机制。

### 9.3 V2
1. 跨地域容灾与更高等级 SLA。
2. 平台化自助治理与租户精细化运营能力。

## 10. 需求风险与待持续确认
1. 2C4G 单 Pod 指标需通过真实业务模型压测验证，存在波动风险。
2. 到达率优先可能牺牲部分实时性，需在产品侧明确容忍阈值。
3. 设备级恰好一次在多端迁移场景下需明确设备身份稳定策略。
4. 会话内有序在大群高并发场景需定义乱序容忍与补偿策略。
