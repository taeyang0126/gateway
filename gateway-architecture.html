Gateway 当前架构全景

本页基于当前代码实现整理，覆盖网关数据平面链路、插件机制、安全体系、 连接池与 H2 复用、可观测性、启动预热和优雅停机策略。可直接作为 架构评审材料和新成员 onboarding 入口。

更新时间: 2026-04-01 Runtime: Java 21 + Netty 4.2.x + Spring Boot 3.4.x 核心模式: Plugin Chain + Async Pool + H2 Multiplexing

0. 边缘流量入口链路

按你指定的业界入口路径，核心请求主干为 CDN域名解析 -> ALB -> Gateway -> Upstream。

Edge Traffic Topology

为什么要先走 CDN（白话版）

  • 用户先命中离自己更近的 CDN 节点，首包更快，页面/接口体感延迟更低。
  • 静态资源（JS/CSS/图片）直接在边缘返回，不用每次都打到源站。
  • 热点流量先在 CDN 被“削峰”，ALB 和 Gateway 压力会小很多。
  • 很多攻击流量会先在边缘被清洗，源站暴露面更小、更安全。
  • TLS 握手可以在边缘终止一部分，减少源站连接开销。
一句话：CDN 做“就近加速 + 缓存抗压 + 第一层防护”，不替代 Gateway 的业务治理能力。

CDN / ALB / Gateway 分工

层 主要职责 不负责什么
CDN + DNS 就近接入、静态缓存、边缘防护、回源调度。 不做业务鉴权和细粒度路由策略。
ALB L7 负载均衡、跨可用区分发、健康检查。 不承担插件链和业务级限流逻辑。
Gateway 鉴权、ACL、限流、路由、观测、上游代理。 不追求全球边缘缓存能力。

域名指向 CDN 的好处和坏处（评审可直接引用）

维度 好处 坏处 / 成本
性能 边缘就近接入，静态资源可直接命中缓存，首包与加载速度更快。 动态接口如果几乎不缓存，收益有限，链路反而多一跳。
稳定性 热点流量在边缘被削峰，源站高峰更稳。 缓存策略配置不当会出现旧数据或缓存穿透问题。
安全 边缘可先做 WAF/抗 DDoS/基础风控，减少源站暴露面。 需要正确透传真实客户端 IP，否则会影响鉴权、限流和审计准确性。
成本 源站带宽和连接压力下降，能降低源站扩容压力。 新增 CDN 请求费、流量费、回源费，整体成本模型更复杂。
运维复杂度 边缘规则统一后，多地域发布更灵活。 排障链路从“源站”变成“DNS + CDN + ALB + Gateway + Upstream”。

实践建议：静态资源域名默认指向 CDN；动态 API 按路径拆分缓存策略（可缓存与不可缓存分开），并固定透传 X-Forwarded-For、X-Forwarded-Proto 等关键头。

1. 总体定位与模块视图

网关目标

  • 作为反向代理入口，提供高性能路由转发与多租户安全控制。
  • 在请求进入上游前，执行可配置的插件链与安全链，支持短路拒绝。
  • 以指标、访问日志、Trace 标签实现可观测闭环，便于生产排障。

仓库模块

  • gateway: 网关主模块（监听 8080）。
  • gateway-pool: 通用异步并发资源池（灵感来自 HikariCP）。
  • example-upstream: 上游 Mock 服务（8082）。
  • example-auth: JWT 签发/校验示例（8091）。
  • gateway-perf: 压测和回归基线。

业界对齐点: 该设计属于典型 Data Plane（请求处理）+ 简化 Control Plane（静态配置） 架构，风格接近 Envoy/Kong 的过滤链模型。

2. 运行时分层架构

Proxy Layer ProxyHandler + UpstreamConnectionPool，HTTP 转发到上游

3. 请求生命周期（核心链路）

traceContext-> drain-> routing-> plugin.request-> proxy-> plugin.response/error-> client

阅读建议：先看时序图把握全局，再看 Step 01-10 了解实现细节，最后看 H2 生命周期图和白话卡片做上下对照。

请求流程时序图

Step 01
Trace 建链 TraceContextHandler 解析/生成 traceparent 与 tracestate，保存 traceId 到 Channel Attribute， 后续转发时可透传给 upstream。
Step 02
连接级预处理 + 排空拦截 RoutingHandler 先记录 keep-alive/close 语义； 若处于 draining，DrainHandler 对非健康检查请求直接返回 503 并关闭连接。
Step 03
路由与系统端点 优先处理 /health、/health/live、/health/ready、/metrics； 其他路径走 RouteResolver，规则为 priority ASC + pathPrefix 长度 DESC。
Step 04
REQUEST 插件链执行 全局/路由配置按插件名合并，路由同名覆盖全局；按 priority 升序执行并记录 插件耗时与决策指标。任一插件返回 short-circuit 时立即响应，不进入上游转发。
Step 05
Proxy 前置校验 ProxyHandler 固化请求级上下文（clientIp、auth 结果、安全决策）； 计算路由级/全局请求体上限，先做 Content-Length 快速校验， 超限直接 413；补充 x-forwarded-* 与 trace 头。
Step 06
异步获取 upstream 连接（池化） 通过 UpstreamConnectionPool.acquire(host, port) 进入 ConcurrentPool.borrowAsync，超时阈值来自 connect-timeout-millis。池满/借用失败会触发 503 或 502 分支。
Step 07
H2 stream 槽位预占与重试 在拿到连接后先 tryReserveStream()；若连接并发流已满，释放连接并重试， 最多 MAX_ACQUIRE_RETRIES=3，超限返回 503。 nextStreamId() 溢出时会退役该连接（retire）并重试。
Step 08
H2 HEADERS / DATA 全流式转发 创建 Http2FrameStream，在 upstream EventLoop 写 HEADERS； 若请求体尚未到齐，先缓存在 pendingContent，stream 建立后再持续写 DATA。 请求体累计大小实时校验，超限返回 413。
Step 09
响应 demux 与插件后处理 H2ResponseDemuxHandler 按 streamId 回调响应头/响应体； 先执行 RESPONSE 阶段插件（响应头加工），再注入 CORS 头并回写客户端； 上游错误进入 ERROR 插件链，可输出自定义错误体。
Step 10
完成收口与资源回收 请求完成时统一写 metrics + access log（含 security 字段）， 并 inFlight--。异常/断连/超时时执行清理：移除 demux 映射、 回收预占 stream 槽位、释放 pending 内容块，防止泄漏。

白话版：一次请求到底做了什么

  • 先给请求打上 traceId，后续每个环节都能串起来排障。
  • 如果服务在下线排空（draining），新请求会快速返回 503。
  • 按路由规则找到目标上游，再执行安全与治理插件做“入场安检”。
  • 安检通过才会进入代理层，去连接池借 upstream 连接。
  • H2 下不是“一连接一请求”，而是一连接跑多个 stream 并发。
  • 请求体会被流式转发，不需要等整包收完，延迟更低。
  • 响应回来后还会过 RESPONSE/ERROR 插件，再返回客户端。
  • 最后统一写指标和日志，并回收槽位/缓存，防止资源泄漏。

术语速记（非网关同学）

H2 Connection 一条 TCP 长连接，可复用。
H2 Stream 连接内的并发“子通道”，一次请求占一个 stream。
Demux 按 streamId 把响应分发回对应请求处理器。
Retire 连接不再接新请求，但允许在途流自然结束。
Short-circuit 插件提前拒绝，直接返回，不再访问上游。
Drain 优雅停机阶段，只清在途，不接新流量。
记忆口诀：先安检、再借连接、占 stream、发数据、收响应、做清理。

H2 Stream 生命周期专图（含异常分支）

H2 连接池与流复用关键路径

阶段 实现细节 失败处理
连接借用 acquire(host,port) -> borrowAsync(timeout)，按 host:port 分池。 借用失败记录 gateway.pool.borrow.failures；返回 502/503。
流槽位预占 demux.tryReserveStream() 原子预占，防止并发 check-then-act 竞态。 流满时释放连接并重试，超过 3 次返回 503。
streamId 分配 nextStreamId() 与 codec 自增同步，用于溢出检测。 溢出时 retire(channel)，避免继续被新请求复用。
连接归还策略 HEADERS 发送路径建立后立即 release(channel)，提升连接复用率。 中间态异常使用 remove(channel) 强制摘除并关闭。
响应分发 demux.register(streamId, proxyHandler)，按 stream 回调头/体/错误。 RST_STREAM/GOAWAY/断连触发 ERROR 链并清理映射。
停机协同 停机阶段通过 hasActiveH2Streams() 轮询活跃流，等待清零。 超时则告警并进入后续停机阶段。

状态码触发矩阵

  • 413: 请求体超过路由或全局限制。
  • 429: IP/用户限流插件拒绝。
  • 401: JWT 认证失败。
  • 403: IP 黑白名单拒绝。
  • 503: draining 或 H2 流控饱和重试失败。
  • 502: upstream 连接失败或 H2 stream 错误。
  • 504: IdleState 超时触发网关超时。

请求体流式细节

  • 连接未就绪时，HttpContent 进入 pendingContent 队列。
  • stream 建立后分批转换为 H2 DATA 帧写入。
  • END_STREAM 场景自动忽略后续空块，避免重复写。
  • 跨 EventLoop 写入统一切换到目标 loop 执行，减少竞态。

收尾与观测字段

  • 请求完成统一写 gateway.requests.* 指标。
  • 访问日志落地 method/path/status/duration/bodySize。
  • 同时记录 authRequired/authPassed/security* 字段。
  • traceId 与安全决策标签用于关联排障。

故障定位速查（技术动作 -> 你会看到什么）

场景 典型信号 第一排查动作
borrowAsync 超时 503 增长，gateway.pool.borrow.failures 上升。 看目标 upstream 的连接上限、RT、实例健康和 ALB 后端状态。
stream 槽位长期打满 503 + 重试次数升高，活跃流接近上限。 检查每连接最大并发流配置，评估是否扩容 upstream 或提升池大小。
HEADERS 写失败 502 抖动，错误链路触发率上升。 排查 upstream GOAWAY/RST、网络抖动、连接被动关闭原因。
请求体超限 413 升高，集中在特定路由。 核对路由级请求体上限配置与客户端发送体积。
插件短路激增 401/403/429 提升，gateway.plugin.decisions 偏拒绝。 按插件名维度看拒绝原因，核查 ACL、JWT、公网出口 IP 变化。

4. 插件体系与安全链（REQUEST 阶段）

设计模式: 可插拔策略 + 统一 PluginContext + 短路控制。 指标维度由 MetricsCollector 统一记录（耗时和决策）。

安全插件顺序图（含拒绝分支）

默认优先级 插件 职责 拒绝/结果
500 cors 处理 CORS，预检请求可直接返回 可短路 204
1000 real-ip 按 trusted-proxies / trusted-proxy-hops 解析真实客户端 IP 透传
2000 ip-access 黑白名单 CIDR 校验（黑名单优先） 403 短路
3000 ip-rate-limit 按 client IP 限流 429 + Retry-After
4000 auth JWT 认证并写入 x-userId 401 短路
5000 user-rate-limit 按 userId 限流（未认证用户可跳过） 429 + Retry-After
6000/6100/6200 add/remove-request-header + rewrite-path 请求头改写与路径正则重写 透传

安全链符合固定顺序要求: real-ip -> ip-access -> ip-rate-limit -> auth -> user-rate-limit。 若中间任意阶段拒绝，则立即终止并返回。

失败策略: 认证与访问控制默认 fail-closed；支持 shadow 模式只记录不阻断。

6. 路由与配置模型

路由字段

  • id, path-prefix, upstream。
  • priority 小值优先，支持同级按 path 长度最精确匹配。
  • timeout-seconds, max-request-size。
  • rewrite-path + rewrite-replacement。
  • plugins 路由级插件覆盖全局同名插件。

全局关键默认值

7. 高性能转发与连接池设计

H2 多路复用

  • 连接获取后先尝试 tryReserveStream()。
  • 执行 streamId 溢出检查，不可用连接退役。
  • 通过 H2ResponseDemuxHandler 做响应分发回调。
  • 流控满载时有限重试，超限返回 503。

连接池获取策略

  • ThreadLocal 快路径。
  • 共享列表 CAS 扫描。
  • 池未满则异步创建连接。
  • 池满则进入 PendingBorrow 队列并计时超时。

资源安全策略

  • remove: 从池中摘除并关闭（不可复用）。
  • retire: 只摘除不立即关闭（保留飞行流）。
  • 定时空闲淘汰，避免长期空闲连接占用资源。
  • 连接池指标按 host:port 注册 Gauge。

9. 启动预热与优雅停机

启动预热（WarmupRunner）

  • 阶段 1: 内部热路径预热（路由匹配 + JSON 编解码）。
  • 阶段 2: 上游预热（按 host:port 去重后主动 acquire/release）。
  • 全局预算由 warmup-timeout-seconds 控制，超时不阻塞启动。

优雅停机（ShutdownCoordinator）

  • 阶段 1: 关闭 serverChannel 与 bossGroup，停止接收新连接。
  • 阶段 2: 激活 draining，新请求快速返回 503。
  • 阶段 3: 等待在途请求和 H2 活跃流清零（可配置超时）。
  • 阶段 4: 先关连接池，再关 workerGroup，避免事件丢失。

10. 业界对标与下一步演进建议

业界能力映射（当前实现 vs Envoy / Kong / Nginx）

当前网关能力 业界同类概念 说明
REQUEST/RESPONSE/ERROR 插件链 Envoy HTTP Filter / Kong Plugin / Nginx phase handlers 都是“可编排过滤器链 + 短路机制”，核心差异在插件生态与控制面成熟度。
RouteResolver（priority + prefix） Envoy RouteConfiguration / Kong Route / Nginx location 本质都是先匹配路由再绑定上游与策略，目标是确定性命中和低开销查找。
UpstreamConnectionPool + H2 多路复用 Envoy Cluster Connection Pool / Kong upstream keepalive 关注点一致：连接复用、并发流控制、异常连接摘除和退役。
ACL + JWT + 限流组合安全链 Envoy ext_authz/jwt_authn/ratelimit / Kong ACL+JWT+RateLimit 业界通常采用“先身份、后配额、再转发”的 fail-fast 模式。
Metrics + AccessLog + TraceContext Envoy stats + access log + tracing 可观测三件套一致，关键在字段标准化和跨系统关联能力。
Warmup + Draining + 分阶段 Shutdown Envoy Drain Manager / Nginx graceful shutdown 共同目标是上线冷启动可控、下线无损，避免连接和在途请求被硬切。

说明：上表是能力模型映射，不代表实现细节完全一致；重点用于架构评审时的“同类能力对照”。

已对齐业界实践

  • 过滤器链短路机制（类似 Envoy HTTP Filter）。
  • 结构化日志 + 指标 + Trace 三位一体。
  • 连接池复用与多路复用并行优化。
  • 优雅停机分阶段编排。

当前边界

  • 配置源以静态配置为主，尚未形成动态控制面。
  • 限流引擎默认本地模式，跨实例一致性有限。
  • 熔断/重试/主动健康探测能力仍可加强。

建议演进路线

  • 引入配置热更新与灰度发布能力（Control Plane 化）。
  • 补充分布式限流后端和失败降级可观测看板。
  • 按 upstream 增加熔断、被动探测与故障隔离。
  • 将插件治理扩展到版本化和兼容契约测试。

结论: 当前网关已具备生产可用的核心基础能力，重点可沿 动态配置、 分布式治理、 故障自治 三条线继续升级。
