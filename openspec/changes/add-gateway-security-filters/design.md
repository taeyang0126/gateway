## Context

当前 `gateway-core` 已具备路由匹配、代理转发、连接池与可观测性能力，但请求进入 `RoutingHandler` 后会直接进入转发流程，缺少统一的安全策略链。现有请求限制以请求体大小和超时为主，尚未提供可配置的 IP 访问控制、认证类型扩展、限流模式切换等能力。

本次变更是跨模块与跨关注点改造，涉及：
- `gateway-core` 请求入口链路、配置模型、错误语义与观测埋点；
- 新增 `auth-jwt-example` 模块用于 JWT 签发与校验联调；
- 未来将扩展更多认证方式与分布式限流依赖。

约束条件：
- 保持现有路由转发行为兼容；
- 失败策略遵循冻结需求：认证/IP `fail-closed`，分布式限流失败降级本地；
- 配置优先级遵循 `merge` 默认与 `replace` 显式覆盖。

## Goals / Non-Goals

**Goals:**
- 在转发前建立统一安全过滤器链，执行顺序固定且可观测。
- 提供认证类型框架，默认 `jwt`，并可平滑扩展其他类型。
- 提供限流模式切换能力：默认本地，支持分布式并带故障降级。
- 提供可信代理下的真实 IP 解析与黑白名单访问控制。
- 统一错误码与错误响应体（401/403/429）并沉淀审计与指标。
- 提供 `auth-jwt-example` 模块用于本地验证。

**Non-Goals:**
- 不在本期实现动态配置中心与管理控制台。
- 不在本期实现复杂 ABAC/PDP 策略编排。
- 不在本期强制引入特定分布式中间件实现细节（由配置与接口抽象承载）。

## Decisions

### Decision 1: 引入统一安全过滤器链抽象

决策：
- 在路由转发前新增安全过滤链（逻辑顺序：真实 IP -> IP 访问控制 -> IP 限流 -> 认证 -> 用户限流）。
- 过滤器统一返回决策结果（ALLOW / DENY / ERROR），并携带拒绝原因码。
- 路由命中后、转发前执行过滤器链；拒绝时短路，不进入上游连接流程。

理由：
- 将策略逻辑从转发细节中解耦，降低后续扩展成本。
- 统一短路语义，避免不同策略实现各自维护错误响应。

备选方案：
- 方案 A：将策略散落在 `RoutingHandler` / `ProxyHandler` 内部。
  - 缺点：耦合高，新增策略需要反复改主链路，测试边界不清晰。
- 方案 B（采纳）：统一过滤器链抽象，主链路只负责编排。

### Decision 2: 采用请求上下文对象贯穿过滤阶段

决策：
- 建立请求级上下文（如 `SecurityRequestContext`），承载 clientIp、routeId、userId、limitKey、decisionReason 等字段。
- 上下文在单次请求生命周期内共享，不跨请求复用。

理由：
- 避免重复解析与重复计算（例如 IP、认证主体、限流键）。
- 便于审计日志与 metrics 统一打点。

备选方案：
- 仅用 Channel Attribute 存散字段。
  - 缺点：字段分散、可维护性差，难以表达过滤阶段语义。

### Decision 3: 真实 IP 解析采用“可信代理 + 头部链路”模型

决策：
- 仅在 remoteAddress 属于 trusted proxies 时解析 `X-Forwarded-For` / `Forwarded`。
- 不可信来源请求忽略代理头，直接使用 socket 源地址。
- trusted proxies 模式下按“从右到左剥离可信代理链”解析真实客户端 IP，取第一个非可信地址。
- 新增 `trustedProxyHops` 可选配置，支持固定可信跳数场景（如前置 LB IP 动态变化）。
- 解析结果作为后续 IP 黑白名单与 IP 限流唯一输入。

理由：
- 防止伪造头部绕过黑白名单和限流。
- 与主流网关（Nginx/Envoy/Kong）可信代理模式一致。

备选方案：
- 无条件信任 `X-Forwarded-For`。
  - 缺点：安全风险高，容易被绕过。

### Decision 4: 配置模型采用“全局基线 + 路由策略”，默认 merge

决策：
- 新增安全配置根（如 `gateway.security`），按过滤器维度拆分子配置。
- 路由策略默认 `merge`，可显式声明 `replace`。
- `replace` 为整段替换，`merge` 仅覆盖显式字段。

理由：
- 满足“全局统一+路由特例”双重诉求，且行为可预测。

备选方案：
- 仅支持全局配置或仅支持 replace。
  - 缺点：前者灵活性不足，后者配置冗余且易误配。

### Decision 5: 认证能力采用类型化 SPI，默认本地 JWT Provider（公钥/JWKS）

决策：
- 定义认证接口层（`AuthProvider`），通过 `auth.type`（枚举）选择实现。
- 将 token 提取策略从 provider 配置中解耦，独立为 `auth.token-extractor`。
- 将 provider 专属配置收敛为 `auth.providers.<provider>`，首期为 `auth.providers.jwt`。
- 首期提供 `jwt` provider，采用本地验签路径；认证失败统一映射 `401`。
- 认证成功后将主体标识写入 `x-userId` 请求头，并覆盖客户端同名头。
- JWT 校验至少覆盖签名、`exp`、`iss`、`aud`。
- 密钥来源支持静态公钥与 `jwks-url` 两种模式。
- `jwks-url` 模式采用本地缓存与定时刷新策略，请求主路径不做每请求远程鉴权调用。

理由：
- 满足当前需求，同时为 API Key/OAuth2 等扩展留接口稳定面。
- 主路径无网络依赖，延迟和可用性更稳定。

备选方案：
- 每个请求调用远程鉴权服务（introspection/ext-auth）。
  - 缺点：增加网络 RTT 与外部依赖故障面，P99 延迟与可用性风险更高。
- 只写死 JWT 逻辑且不支持密钥来源扩展。
  - 缺点：后续扩展将产生破坏式改造。

### Decision 6: 限流引擎抽象为 Local/Distributed 双实现 + 降级

决策：
- 定义统一 `RateLimiterEngine` 接口。
- 限流配置拆分为独立的 `ip` 与 `user` 两个限流器，公共参数抽取复用。
- `ip` 限流键仅包含 `clientIp`，`user` 限流键仅包含 `userId`。
- 默认 `local`（进程内令牌桶），支持 `distributed` 模式。
- `distributed` 出错时按冻结需求自动降级为 `local`，并产生降级事件。
- 限流拒绝统一返回 `429` + `Retry-After`。

理由：
- 在可用性与一致性之间保持可配置平衡，先确保可运行再提升集群一致性。

备选方案：
- 一刀切只做 distributed。
  - 缺点：依赖外部系统，故障面大，初期运维成本高。

### Decision 7: 统一错误语义与可观测事件模型

决策：
- 过滤器拒绝统一输出结构化错误体，状态码固定映射：
  - 认证失败：401
  - 策略拒绝：403
  - 限流拒绝：429
- 指标维度至少包含 `filter`, `decision`, `reason`, `routeId`。
- 审计日志统一字段：traceId、clientIp、routeId、filterName、decision、reason。
- 访问日志新增安全相关字段：`authRequired`、`authPassed`、`securityDecision`、`securityFilter`、`securityReason`。
- 对安全链拒绝请求同样输出访问日志，避免仅在放行转发路径记录访问日志。

理由：
- 统一排障口径，减少线上“同类问题不同格式”成本。

备选方案：
- 各过滤器各自返回错误体与日志结构。
  - 缺点：观测和排障碎片化。

### Decision 8: 新增 `auth-jwt-example` 示例模块作为验收基座

决策：
- 新增独立模块提供最小 JWT 签发与校验用例及联调入口。
- 示例模块用于回归验证认证链路与配置可用性。

理由：
- 快速验证设计可落地，降低接入方理解成本。

备选方案：
- 仅在 `gateway-example` 临时拼接示例。
  - 缺点：边界不清，示例与通用演示耦合。

## Risks / Trade-offs

- [可信代理配置错误导致真实 IP 识别偏差] -> 提供启动期配置校验与告警日志，并给出默认安全回退（使用 socket 源 IP）。
- [过滤链新增处理增加延迟] -> 对每个过滤阶段采集耗时指标，压测验证并优先优化高开销点（认证与分布式限流）。
- [分布式限流降级逻辑被忽视] -> 降级事件做显式 metrics/log 告警，并在运维文档中给出阈值与处置流程。
- [merge/replace 语义被误解] -> 在配置文档中给出同字段示例与冲突规则，增加单元测试覆盖继承行为。
- [认证类型扩展后接口漂移] -> 通过 SPI 接口契约测试保证新增 provider 不影响既有 jwt 行为。

## Migration Plan

1. 第一步：引入过滤器链抽象与统一错误响应，不改变默认策略（全关闭）。
2. 第二步：落地真实 IP 解析与 IP 黑白名单（先 shadow，后强制）。
3. 第三步：接入 JWT 认证与本地限流，完善指标和审计日志。
4. 第四步：接入分布式限流实现与自动降级机制，完成故障演练。
5. 第五步：新增 `auth-jwt-example` 模块并纳入回归测试。
6. 回滚策略：按过滤器开关逐级回退；出现异常时优先关闭新增过滤能力，保留核心转发链路。
